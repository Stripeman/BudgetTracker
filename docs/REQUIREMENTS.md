| BT-014-01 | Cascade/impact engine and per-record permanent deletion (`api/_shared/deletion.js`) | Built with tests. Implements Terry's rule exactly: a record alone, or one single dependent relationship with no further dependents of its own, may be permanently deleted after two confirmations; branching to more than one kind of dependent, or a second hop, is refused, and separate dependency groups are never combined to make an otherwise-blocked operation look allowed. Every type wired: **accounts** (`POST /api/accounts?action=delete-impact/delete-permanent`) — cascades to its own transactions or, exclusively, its own recurring bills (never both: branching blocks); a transaction that is one leg of a transfer whose other leg is on a different, untouched account always blocks (Terry's resolution 1), as does a bill on another account that transfers into this one, a Shared-expenses link on the account no longer blocks (Part A, 2026-09-17): groups.foreignWorkspaceIds documents why every shared expense in this codebase is managed solely by one workspace today (no cross-workspace participation model exists), so the account's group ledger link is severed as a non-branching auto-cleanup step (removed, not merely ended, because the shared invariant checker requires every link to resolve to a real account) while the shared expense's amounts, splits, payers, shares, settlements and history are preserved untouched; the client is offered a CSV/JSON/XLSX/PDF download of the authorized Shared-expenses data first (BT-014-06); the (still unbuilt) sever-for-a-real-foreign-workspace/preserve-for-others/sole-manager-handoff branch would only ever trigger if that function ever finds a real foreign workspace id, which it cannot yet; linked grants are cleaned up automatically (not counted as branching, since a grant cannot mean anything without its resource). **transactions** — a transfer's other leg or a reversal pair is removed together as the same event (never counted as a cascade dependency); Shared-expenses-recorded entries, either half of a hand-entered owed pair, and reconciled entries stay blocked exactly as the existing soft delete already blocks them. **merchants** (`api/payees`, gained permanent deletion for the first time — previously archive-only) — entries that reference it keep everything else and simply lose the link, proving Terry's own example in reverse ("deleting a transaction must not delete its merchant" implies the reverse too: deleting a merchant must not delete the entries that reference it). **categories** — blocked while any budget's current lines, or any subcategory, still use it (a conservative, deliberate choice: rather than silently rewriting a budget's lines or risking an empty budget); otherwise severed from transactions, splits and merchant defaults. **recurring bills** — no cascade dependents (skips/pauses/resumes are embedded, not a separate record type); an entry already recorded from it keeps its amount and everything else and just loses the link back to the bill. **budgets** — nothing else references a budget by id, so it is always deleted alone. **contacts** — workspace-scoped only (see limitation below); blocked while referenced as an entry's responsible person or anywhere in Shared-expenses history, otherwise deleted freely. Every execute call recomputes the impact fresh and refuses if it drifted since the caller reviewed it (a short fingerprint token) or if the typed confirmation phrase (the record's own name, or a fixed "DELETE" for transactions, which have none) does not match exactly; a genuinely blocked attempt is still audited (`<type>.delete-blocked`); a completed one writes one atomic audit entry (`<type>.delete-permanent`, actor, target, affected counts by type — never ids or values) in the SAME write as the removal, and the deleted record's own prior audit entries (create, update, archive, …) survive it untouched, because the audit array is never touched by any `apply` function. Every deletion re-validates the resulting document with the exact invariant checker `api/_shared/backup.js` uses for backups (`checkInvariants`), so a bug here can never ship a dangling reference a later backup or restore would refuse — proven by a test that takes a real on-demand backup after several permanent deletions. Rename needed no new work: every one of these types already accepts a `name` change through its existing PATCH route (verified with a test), so authority mirrors edit authority automatically. **Evidence:** `api/test/deletion.test.js`, 15 tests: "A alone", one-relationship cascade, branching blocked, cross-account transfer-leg blocked, permission mirrors edit authority (member/viewer/outsider/cross-owner all refused correctly), stale-impact-token refused, wrong-typed-confirmation refused, transfer legs removed together, merchant severed while an entry keeps its amount, category blocked-by-budget then severed-and-deleted, recurring severed, budget deleted alone, contact blocked-then-deleted, the post-deletion backup proof, and the rename-via-PATCH proof.
